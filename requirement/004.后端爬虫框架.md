## 架构规划

### 分层设计与核心模式应用
为了实现引擎透明化与运行时策略调度，系统被划分为四个核心层次。这种分层结构确保了底层解析引擎的更换不会波及上层业务逻辑，同时为异步处理提供了坚实的基础。
系统分层模型与逻辑流向
| 层次名称 | 核心组件  | 职责描述 |
| -------- | -------- | -------- |
| 应用接口层 | CrawlController, WebSocketHandler | 处理爬取任务的接收、异步反馈及WebSocket连接维护 |
| 门面与调度层 | CrawlFacade, AsyncManager | 作为系统入口屏蔽底层细节，协调异步任务的生命周期与通知触发 |
| 策略路由层 | CrawlStrategyFactory, StrategyResolver | 基于URL特征、SEO标记或配置中心决定采用Jsoup还是Playwright引擎 |
| 执行引擎层 | JsoupEngine, PlaywrightEngine | 负责具体的网络请求、内容提取、动态渲染及异常处理 |

### 门面模式
屏蔽引擎差异的统一入口
门面模式在本项目中体现为CrawlFacade接口。调用方仅需传递一个包含目标URL、所需字段选择器（CSS/XPath）以及任务元数据的请求对象。CrawlFacade封装了复杂的工厂查找、策略匹配和结果聚合过程。这种设计遵循了“对扩展开放，对修改关闭”的原则，使得系统在未来引入如AI辅助解析（LLM-based parsing）等新引擎时，前端调用逻辑无需任何改动。

### 策略模式
动态决策执行引擎
爬虫引擎的选择不应是静态的。策略模式通过CrawlStrategy接口及其具体实现（JsoupStrategy和PlaywrightStrategy）提供了灵活的运行时切换能力。决策过程由StrategyResolver完成，它会根据以下因素进行权重评估：
1. URL域名规则：预先配置的动态站点清单。
2. 预爬取嗅探：通过轻量级的HEAD请求或初步的GET请求检查HTML内容，识别是否存在单页应用（SPA）常见的挂载点，如<div id="app"></div>，当使用自动策略时，若HTML内容中包含该挂载点，默认选择Playwright引擎。
3. 用户偏好：请求参数中明确指定的执行模式。

## 执行引擎的深度实现
Jsoup与Playwright
两个引擎虽然在功能上存在交集，但在底层的资源管理和线程模型上有着本质区别。

### Jsoup
轻量化静态解析的高效实践
Jsoup在解析不需要JavaScript执行的静态页面时表现卓越。在JDK 25的虚拟线程环境下，Jsoup的同步网络调用会被JVM优雅地挂起，而不会阻塞底层平台线程。
在实现JsoupStrategy时，必须配置合理的连接参数。Jsoup 1.22.1支持更细粒度的HTTP头控制，这对于绕过简单的反爬机制至关重要。
• User-Agent 模拟：随机化UA池以降低单一标识被封锁的概率。
• 超时管理：利用Jsoup的.timeout()方法配合Spring的弹性退避策略，确保在遇到慢速连接时不会导致任务积压。

### Playwright
重型动态渲染与线程安全挑战
Playwright提供了完整的浏览器仿真能力，能够处理复杂的AJAX请求、影子DOM以及Canvas内容。然而，Playwright Java版并非线程安全，这意味着所有的操作必须在创建该实例的线程内执行。
针对该限制，结合JDK 25虚拟线程的架构方案如下：
1. Thread-Per-Task 模型：由于虚拟线程极其廉价，不再建议使用复杂的浏览器实例池。相反，可以为每个爬取任务启动一个独立的Playwright实例，并利用try-with-resources块确保在任务完成后自动释放浏览器进程。
2. BrowserContext 隔离：每个任务使用独立的BrowserContext，这相当于开启了一个全新的无痕窗口，能够有效隔离Cookies、LocalStorage和会话状态。
3. 信号量控制（Semaphore）：尽管虚拟线程允许创建大量任务，但由于启动浏览器进程是CPU和内存密集型操作，必须使用java.util.concurrent.Semaphore来限制全局活跃的Playwright任务数量，防止系统过载。
异步任务生命周期与WebSocket实时通知

### 异步任务
由于爬取任务可能持续数秒至数分钟，同步等待显然不可取。系统需构建一个从请求入队到异步反馈的完整链路。
基于任务ID的异步启动流程
当控制器接收到任务请求时，通过AsyncManager启动一个受虚拟线程池管理的后台任务，并立即向客户端返回一个唯一的taskId。此时，前端可以展示进度条或进入状态监听模式。
Spring Boot 4的异步执行器可以通过配置轻松对接虚拟线程：
@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean
    public TaskExecutor applicationTaskExecutor() {
        return new VirtualThreadTaskExecutor(); // JDK 25 原生支持
    }
}

### WebSocket实时通知
WebSocket/STOMP 通信协议设计
为了实现高效率的通知，系统采用STOMP作为WebSocket的子协议。相比原始WebSocket，STOMP提供了基于“目的地”的消息路由，更适合复杂的异步系统。
1. 握手与建立：客户端连接至/ws-crawler端点，并订阅/topic/tasks/{taskId}。
2. 中间状态推送：爬虫在执行过程中（如翻页、数据抽取中）可以利用SimpMessagingTemplate推送任务进度百分比。
3. 最终结果推送：任务完成后，系统将标准化后的JSON对象封装在通知帧中发送至该目的地，并断开或保持连接待命。

### 统一数据模型
标准化JSON响应封装
数据一致性是爬虫平台的生命线。无论底层是Jsoup提取的DOM片段，还是Playwright截取的XHR响应，最终都必须由ResultStandardizer组件转化为统一的DTO（Data Transfer Object）。

### 弹性与韧性
重试、限流与异常处理
在真实的网络环境中，爬取失败是常态。Spring Boot 4整合了原生的弹性调度注解，使得构建韧性系统变得极其直观。
重试策略与退避算法
针对网络超时、503服务不可用等瞬态故障，可以使用@Retryable注解配置自动重试。
• 指数退避（Exponential Backoff）：设置multiplier = 2，让重试间隔从1s、2s、4s递增，避免给目标服务器造成持续的突发压力。
• 特定异常捕获：仅针对ConnectException或GatewayTimeoutException进行重试，而对于404 Not Found或权限验证失败则立即终止并上报。
并发限制与熔断
使用@ConcurrencyLimit注解可以有效控制对特定域名的访问频率，防止因爬取速度过快被目标网站防火墙阻断。结合JDK 25的虚拟线程，这一机制可以保护载体线程不被长时间运行的任务占满，确保系统核心服务的可用性。
总结：构建可扩展的现代爬取平台
通过整合Spring Boot 4的模块化架构与JDK 25的并发特性，本设计提供了一个兼顾灵活性与性能的爬虫解决方案。门面模式成功解耦了业务需求与技术实现，而策略模式确保了系统在面对复杂Web页面时的自适应能力。异步非阻塞的任务模型配合WebSocket实时通知，解决了长作业环境下的交互痛点。在Jackson 3和Servlet 6.1的加持下，该系统不仅具备了卓越的解析性能，更在安全性与标准合规性方面达到了工业级标准。
