# 项目开发规范

project_root/                                          # 项目根目录

    ├── frontend/                                      # 前端目录
    ├── .gitignore                                     # git忽略文件
    └── README.md                                      # 项目说明文件

## 版本控制规范

### 分支策略

- `main`：生产环境代码
- `develop`：开发主分支，所有功能开发都在这个分支上进行，所有代码都需要先合并到develop分支，再从develop分支创建新的功能分支
- `feature/*`：功能分支，当有新功能开发时，从develop分支创建一个新的功能分支，分支名称为`feature/功能描述`，如`feature/add_user_registration`
- `hotfix/*`：生产环境代码紧急修复分支，当在生产环境发现紧急问题时，从main分支创建一个新的修复分支，分支名称为`hotfix/问题描述`，如`hotfix/fix_user_login_error`

### 提交信息格式

```
<type>: <subject>
<body>
```

**Type类型**：

- `feat`：新功能
- `fix`：bug修复
- `docs`：文档修改
- `style`：代码格式修改
- `refactor`：代码重构
- `test`：测试相关
- `chore`：构建或辅助工具修改

**示例**：

```
feat: 添加用户注册功能
- 实现用户注册接口
- 添加邮箱验证功能
- 完善参数校验
```

## 代码审查规范

### 审查要点

- 代码是否符合本规范
- 是否有潜在的性能问题
- 是否有安全漏洞
- 单元测试是否充分
- 注释是否清晰完整

### 审查流程

1. 开发者提交Pull Request
2. 至少2名团队成员进行代码审查
3. 审查通过后合并到目标分支
4. 审查不通过需修改后重新提交

## 构建和部署规范

### 部署流程

1. 代码合并到develop分支
2. 自动化构建和测试
3. 部署到测试环境
4. 测试通过后合并到main分支
5. 部署到预发布环境
6. 部署到生产环境

## 团队协作规范

### 沟通机制

- 每日站会：9:30-9:45
- 项目进度同步：每周五下午

### 责任分配

- 每个模块指定负责人
- 代码审查实行轮值制度
- 问题跟踪使用统一的issue管理系统

### 知识共享

- 每月技术分享会
- 代码库维护README.md文档
- 重要设计决策记录在docs/design目录
